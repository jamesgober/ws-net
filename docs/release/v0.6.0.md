# ws-net v0.6.0 - Optimisation

**Measured against tungstenite and against itself.** v0.6.0 added a
competitor harness and a benchmark workflow on GitHub's hosted runners,
then worked on what they showed. Streamed text got one validation pass
instead of two, client masking keys came from the OS in batches, the
handshake record became one allocation, and the frame writer lost its
per-frame validation. Allocation failure while reassembling a message now
fails the connection instead of aborting the process.

## Against tungstenite 0.30.0

On the same wire bytes, on Linux, macOS, and Windows runners in one run
(ratio: tungstenite's median over ws-net's):

| Workload | Linux | macOS | Windows |
|---|---:|---:|---:|
| Receive 100,000 small masked messages | 2.34 | 1.95 | 2.34 |
| Send 100,000 small messages, server | 2.55 | 2.12 | 4.83 |
| Send 100,000 small messages, client | 1.47 | 1.93 | 3.52 |
| Accept 10,000 browser upgrade requests | 1.07 | 1.11 | 1.38 |
| Receive one 1 MiB binary message | 0.19 | 1.02 | 1.17 |
| Receive one 1 MiB text message | 0.64 | 1.08 | 1.08 |

The two 1 MiB rows on Linux were left open with their likely cause. The
crate's own benchmark measured the same path on the same runner level with
tungstenite (76 µs against 77 µs binary), so the harness's fresh 1 MiB
allocation per iteration is the suspect, not the parser. The 0.9.x pass
investigates it. `docs/PERFORMANCE.md` has every number and the method.

## What changed

- **Text validated once.** A streamed text message was validated as it
  arrived (for fail-fast) and then again as a whole to produce its `&str`.
  It is now assembled from pieces validated once, with a sequence cut at a
  read boundary carried into the next read and checked as a prefix at once,
  so an invalid byte still fails the moment it arrives. Receiving 1 MiB of
  text got 42 to 60% faster than 0.2.0.
- **Masking keys in batches.** `Connection::client` read its keys from the
  OS cryptographic source 256 at a time: about 1.4 ns per key against about
  40 ns for SHA-1 counter mode over an OS seed. Client sends got 2 to 2.6
  times faster. `client_with_seed` kept SHA-1 counter mode for `no_std` and
  reproducible tests. A refill that fails refuses the send.
- **One allocation per handshake.** The server handshake kept its target,
  `Host`, `Origin`, protocols, and extensions in one exactly-sized buffer.
- **Direct frame writer.** Headers are written straight into the output.
  Small sends still cost about 2.4 ns more than in 0.2.0 on Linux (12 to 24%
  on Linux and Windows; macOS measured faster). That is the price of the 0.4
  output budget and counters, and it was recorded as an accepted cost.
- **`WsError::AllocationFailed` (1011).** Reassembly memory is reserved
  with `try_reserve_exact`, so exhaustion fails one connection, not the
  process.
- `PreparedMessage`'s `Debug` printed lengths only.

## Decisions

The 32-byte masking lanes were not adopted: the existing loop already ran
far above the 20 GiB/s target. No separate ASCII fast path was added: the
standard validator already checks a word at a time, and the cost was the
second pass. permessage-deflate moved out of 1.0 to 1.1: no first-party
DEFLATE crate existed.

## Compatibility

Additive: one new error variant (`AllocationFailed`, `#[non_exhaustive]`
enum). Masking keys from `Connection::client` are drawn differently but
remain unpredictable to the peer, and the wire format is unchanged.
